Version: 1.0

PURPOSE OF THIS DOCUMENT
========================

This document is the complete working brief for the next major version of Kiarash Jalali's personal portfolio. It is intentionally detailed enough to hand to another model, designer, illustrator, motion artist, or developer without losing the original intent.

This is NOT a request to "make the current site prettier."
It is a plan to turn the portfolio into a small illustrated world.

The existing portfolio is technically solid and visually competent, but the new goal is to make it unmistakably personal: artistic, playful, fantastical, culturally specific, and memorable without losing the clarity of a professional front-end portfolio.

Kiarash is a front-end developer, not a professional illustrator. That is not a weakness the design needs to hide. It defines the production strategy:
- Kiarash can build systems, interactions, state, animation logic, responsive layouts, and integrations.
- Art assets can be generated collaboratively, sourced legally, commissioned later, or created with learnable tools.
- The site should use the best technical approach for the desired result, not the easiest approach.
- JavaScript should remain the main implementation language, but specialist libraries are welcome where they materially improve quality.
- The project should remain understandable and maintainable by Kiarash rather than becoming an opaque demo built entirely by a framework or shader expert.

The guiding idea is:

    BUILD THE SITE AROUND THE WORLD.
    DO NOT BUILD THE WORLD AROUND THE OLD SITE.

The pond, Middle-earth homage, illustrative textures, water motion, characters, map-like details, decorative objects, and fantasy interactions become the visual system. Existing futuristic gradients, glassy neon accents, sterile minimalism, and unrelated "tech portfolio" styling should gradually leave.

6. WATER MOTION SPECIFICATION
===============================================================================

The water should never look like a generic WebGL ocean shader.

We want 2D illustrated water whose motion comes from distortion.

Recommended visual recipe:
- pre-painted water texture
- pre-painted caustic texture
- low-frequency displacement noise
- a dynamic ripple/displacement field
- multiple parallax speeds
- slightly quantized art update rate

Three kinds of motion:

A. AMBIENT WATER BREATHING
- very slow
- 8–20 second cycles
- 1–4 px visual movement at normal scale
- mainly in caustic/reflection layers
- almost imperceptible if staring at text

B. LOCAL FISH WAKE
- generated behind a moving fish
- soft directional distortion
- can affect reflection and caustic layer
- fades over 1.5–4 seconds
- stronger when a fish speeds up or turns

C. RING RIPPLES
Triggered by:
- fish occasionally touching surface
- fish clicking / interactions
- falling petal
- optional pointer click on open water
- lotus movement
- rare environmental events

Ripples should distort the image rather than simply draw perfect circles on top.

Performance rule:
Do not run a full physical fluid simulation for the entire viewport unless a prototype proves it adds visible value.
A lower-resolution ripple map (for example 256–512 px) rendered to texture and used as a displacement source can look better and cost much less.

12. HOBBIT-HOLE DOOR INTERACTION
===============================================================================

Concept:
A hobbit-home door exists in the background / side of the Skills or Work zone.

Idle state:
- round painted door
- grass roof
- flowers / stones / warm window
- subtle environment loop
- occasional leaf movement
- optional little smoke from chimney

Interaction:
On click/tap:
1. latch moves
2. door opens inward
3. interior warm light appears
4. a small hobbit steps / leans into view
5. hobbit waves
6. optional second small gesture selected randomly
7. hobbit retreats
8. door closes
9. short cooldown prevents spam

Duration:
approximately 4–8 seconds.

Visual frame rate:
12–18 fps if sprite-animated.
This supports the old-animation / storybook feel.

Best production options:

OPTION A — SPRITE SHEET (recommended for painterly art)
- Generate / draw key poses.
- Clean them manually.
- Interpolate or draw in-betweens.
- Export atlas.
- PixiJS plays animation.
Advantages:
  * painterly texture preserved
  * reliable in browser
  * simple runtime
  * can be very stylized
  * no complicated rig
Disadvantages:
  * more asset work

OPTION B — RIVE
Good if the door / hobbit design becomes more vector / illustrated than painterly.
Rive supports interactive state machines and web runtimes.
Use if:
- we want hover/click states
- we can recreate art as layered vector/raster-friendly components
- we want visual animation authoring rather than coding every pose

OPTION C — SPINE 2D
Best if we want a sophisticated skeletal character rig and are willing to adopt its editor/licensing workflow.
Spine has official runtimes for PixiJS, Three.js, Canvas, WebGL, etc.
This would be useful for a reusable Gollum character more than a one-shot door.

Recommendation:
Use sprite animation for the door sequence first.
Do not introduce a character-animation tool only for one interaction.

13. GOLLUM SYSTEM — "A CREATURE THAT LIVES IN THE PAGE"
===============================================================================

Gollum is not a clickable mascot.
He is a rare autonomous page event.

Core states:
- hidden
- sneak
- watch
- crawl
- climb
- sit
- sleep
- steal-word
- inspect-object
- find-ring
- ring-slip
- angry
- escape

He should NOT always be visible.

Spawn logic:
- only inside the Middle-earth zone
- minimum delay after page load
- event interval randomized
- for example one meaningful event every 45–100 seconds
- do not guarantee events on short visits
- never run several major events simultaneously
- use a seedable/event scheduler for debugging

Example weighted event table:
- 30% sneak across edge
- 20% sit/watch
- 15% sleep briefly
- 15% climb a card / heading
- 10% steal a word
- 7% find-ring sequence
- 3% rare special sequence

Exact weights should be adjusted after watching it in practice.

Gollum should have a "director" that understands:
- current scroll location
- visible section
- available safe space
- whether a modal is open
- whether user is interacting with a form
- device size
- reduced-motion preference
- last event time

If conditions are bad, he stays hidden.

14. GOLLUM WORD-STEAL SYSTEM — OPTIMIZED DESIGN
===============================================================================

User's original idea:
Randomly select a word in a live page element near him, preferably the line he is standing on; Gollum steals it; word disappears; he runs away. Rare, around once per minute at most.

Do NOT scan and tokenize the whole DOM every animation frame.

Recommended architecture:

A. BUILD ELIGIBLE TEXT INDEX ONLY WHEN NECESSARY
On:
- Middle-earth zone activation
- language change
- major responsive resize
- content rerender

Collect candidate text containers:
- paragraphs
- headings
- skill labels
- project descriptions
Exclude:
- links
- buttons
- form controls
- code
- live-demo iframe
- nav
- hidden elements
- aria-live regions

B. EVENT-TIME CANDIDATE SEARCH
Only when a steal event is selected:
1. Get Gollum's planned baseline Y.
2. Check cached eligible containers currently visible.
3. Use DOM Range APIs to locate words / client rects.
4. Score words by:
   - vertical distance from Gollum
   - word length (prefer 4–12 characters)
   - available horizontal room
   - not punctuation-only
   - not brand / important action label
5. Pick from top few candidates with randomness.

C. VISUAL STEAL WITHOUT LAYOUT COLLAPSE
When a word is selected:
- isolate the word with a temporary span
- preserve its exact layout width
- visually hide original characters without collapsing the line
- create an absolutely-positioned clone above the world canvas / DOM
- mark clone aria-hidden
- Gollum reaches for the clone
- clone attaches to hand / bag / body
- Gollum leaves

Do NOT cause paragraph reflow.
Reflow would make the page jump and make the trick feel broken.

D. ACCESSIBILITY
The semantic text should remain available to screen readers.
The "stolen" version should be purely visual.
Do not actually delete important DOM text.

E. RESTORE
After:
- Gollum exits
- 8–20 seconds
- section leaves viewport
- language changes
restore visual word normally.

F. SAFETY / UX RULES
Never steal:
- email address
- form text
- project button labels
- headings currently targeted by navigation
- anything inside the active modal
- a word the user is selecting
- a word inside the iframe

22. MOTION LANGUAGE
===============================================================================

Three animation tiers:

TIER 1 — AMBIENT
Always or frequently active:
- water drift
- subtle reflections
- leaf sway
- fish movement
- very faint caustics
Visual cadence:
- 12–24 fps aesthetic
- low amplitude

TIER 2 — RESPONSIVE
Triggered by user:
- fish avoid / approach
- water click ripple
- door opening
- card lift / physical response
- lotus small displacement
Cadence can be smoother internally for responsiveness.

TIER 3 — RARE STORY EVENTS
- Gollum steals word
- Gollum sleeps
- ring event
- unusual fish behavior
- petal falls
- cat eyes appear
These should remain memorable because they are rare.

Rule:
If everything moves, nothing feels alive.

===============================================================================
23. TECHNOLOGY CHOICE — RECOMMENDED STACK
===============================================================================

Keep the site primarily vanilla JavaScript / semantic HTML / CSS.

Add specialist libraries only where they solve a real visual problem.

RECOMMENDED CORE GRAPHICS ENGINE: PIXIJS 8
-------------------------------------------

Why:
- purpose-built high-performance 2D renderer
- supports sprites, masks, dynamic textures, custom meshes, shaders, blend modes
- mouse / touch interaction
- asset loading
- good fit for painterly 2D worlds
- WebGL production path is mature
- can use GPU-accelerated displacement / filters
- supports custom shaders for water
- far more appropriate than Three.js for a primarily 2D painted pond

Official docs currently recommend WebGL renderer for production, while WebGPU remains less predictable across browsers.

Use PixiJS for:
- pond scene graph
- fish
- lotus / petals
- ripple render texture
- underwater mosaic layers
- texture displacement
- Gollum sprite runtime if sprite-based
- Hobbit-door sprite animation
- environmental particles
- scene culling

Do NOT use PixiJS for:
- body text
- navigation text
- forms
- project content
- accessibility-critical UI

Those stay HTML.

SCROLL / CHOREOGRAPHY: GSAP + SCROLLTRIGGER
--------------------------------------------

Use ScrollTrigger for:
- world transition progress
- parallax between layers
- moving from pond to land
- Middle-earth to pond return
- project chapter reveals
- door / prop trigger ranges
- synchronized CSS / DOM transitions

Why:
- robust scroll position system
- responsive recalculation
- callback / timeline control
- less manual scroll math
- suitable for long narrative page sections

Do not use it to scroll-jack the page.
Normal scrolling remains normal.

CHARACTER ANIMATION OPTIONS
---------------------------

RIVE:
Use if we want:
- interactive vector / hybrid illustrated components
- state-machine driven animation
- designer-visible state logic
- responsive character / UI assets

Rive is especially attractive for:
- animated emblems
- magical dialog seals
- door mechanisms
- UI ornaments
- simpler characters

SPINE:
Consider if Gollum becomes sophisticated enough to justify:
- skeletal character animation
- animation blending
- reusable pose system
- procedural manipulation

Spine officially provides runtimes for PixiJS and web environments.
However, it introduces an editor / licensing workflow and more production complexity.

Recommendation for v1:
- PixiJS + sprite sheets / layered parts
- GSAP ScrollTrigger
- no Spine until Gollum art proves we need it
- Rive only for specific UI/character assets where it clearly helps

THREE.JS:
Do NOT make Three.js the default pond engine.
Three.js has excellent water / reflection examples and GPU water simulations, but the target is a 2D illustrated pond, not a 3D ocean.

Potential later use:
- a special 3D map artifact
- actual perspective / camera scene
- sophisticated reflective 3D object

Not needed for the main design.

===============================================================================
26. PERFORMANCE STRATEGY
===============================================================================

Quality matters, but a portfolio that burns a laptop GPU is a bad portfolio.

DESKTOP TARGET:
- maintain responsive interaction
- GPU canvas can render at display refresh if needed
- art motion may intentionally step at 18–24 fps
- cap internal resolution around 1.5–2x DPR
- high-resolution textures only where visible

MOBILE TARGET:
- fewer fish
- fewer lotus layers
- smaller ripple map
- lower DPR
- lower shader resolution
- Gollum events simpler or disabled on very small screens
- world transitions simplified
- no huge 4K texture decoded unnecessarily

IDLE / BACKGROUND:
- pause scene when document hidden
- IntersectionObserver or world visibility
- stop expensive updates when zone far offscreen
- texture atlases
- object pooling for ripples / particles
- no DOM rect measurement every frame
- no giant full-page canvas with high DPR if not needed

The "low-framerate art" goal helps performance.

- dimensions reasonable

- correct format
- not loading unnecessarily

- How dark must the water be for readability?
- Can fish pass under / over different layers convincingly?
- Does the tile stay subtle?
- Does the site still feel professional?

49. SUCCESS CRITERIA
===============================================================================

The redesign is successful when:

1. A visitor can identify the site from a screenshot without seeing the logo.
2. The pond feels like an authored illustration, not a JS effect demo.
3. Persian visual identity is present without becoming ornamental overload.
4. The Middle-earth chapter is playful and recognizable but still serves Skills/Work.
5. Gollum feels like a rare living creature, not a mascot animation.
6. The website remains easy to navigate.
7. Rootine and project work remain central.
8. The site performs well on a normal laptop and phone.
9. Animation feels deliberate and painterly.
10. The result feels like Kiarash's personal world rather than a design trend.
11. The art system could be expanded later without redesigning the whole site.
12. Kiarash can still understand and modify the JavaScript architecture.

50. FINAL DECISION / NORTH STAR
===============================================================================

The final site should NOT be described as:

    "a dark developer portfolio with fish"

It should be describable as:

    "a hand-painted interactive portfolio world:
     a Persian-turquoise garden pond,
     a brief Middle-earth fan-homage journey,
     and a moonlit return to the water—
     with real project work living inside it."

That is the north star.

When a future design decision is unclear, ask:

    DOES THIS MAKE THE WORLD FEEL MORE COHERENT,
    MORE PERSONAL,
    AND MORE ALIVE—

    OR DOES IT JUST ADD AN EFFECT?

If it only adds an effect, do not add it.
